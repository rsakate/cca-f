1.1 — The Agentic Loop & stop_reason

An agentic loop is NOT a for-loop with a fixed iteration count. It runs until Claude says it is done. The mechanism is stop_reason.

stop_reason Values

ValueMeaningYour Code Does
"tool_use"Claude wants to invoke a toolExecute the tool, append result as user message, loop again
"end_turn"Claude finished its responseExtract text from content[], break out of loop
"max_tokens"Response cut at token limitLog warning; consider summarizing and retrying
"stop_sequence"Custom stop string matchedTreat as end_turn unless you have specific logic
"pause_turn"Server-side iteration limit reached (default 10)Send assistant response back to continue processing
"refusal"Claude declined to respondHandle refusal, possibly rephrase request

The Loop Pattern

response = client.messages.create(
    model="claude-sonnet-4-6",
    messages=messages,
    tools=tools
)

while response.stop_reason == "tool_use":
    # Extract tool_use blocks from response
    tool_block = response.content[i]  # type: tool_use
    # Execute tool externally
    result = execute_tool(tool_block.name, tool_block.input)
    # Append assistant msg + tool_result to messages
    messages.append({"role":"assistant","content":response.content})
    messages.append({"role":"user","content":[{
        "type":"tool_result",
        "tool_use_id": tool_block.id,
        "content": result
    }]})
    # Loop again
    response = client.messages.create(..., messages=messages)

Scenario in Practice

Customer Support Resolution Agent: The agentic loop calls get_customer and receives stop_reason: "tool_use", so it continues. The agent then calls lookup_order and process_refund in sequence, each time looping on "tool_use". Finally, the agent composes a confirmation message and returns stop_reason: "end_turn", signaling the loop to break.

Structured Data Extraction: When extracting invoice data from an unstructured PDF, the agent calls an extraction tool and gets stop_reason: "tool_use". It then calls a validation tool to check the output against a JSON schema. If validation fails, the loop continues with a correction tool call — only when the validated result is ready does "end_turn" fire.

The agentic loop checks stop_reason, NOT a fixed iteration count or natural language like "I'm done". Tool results are appended back as user messages with tool_result blocks. Checking response text for "done" is an anti-pattern.

Iterate-Until-Passing Pattern

When generating code, the agentic loop should run tests and auto-fix failures:

Write code
→
Bash: run tests
→
Parse failures
→
Edit fixes
→
Re-run tests

Test failures are actionable feedback, not terminal errors. The agent parses Bash output, identifies what failed, uses Read/Edit to fix the code, and loops until tests pass. Same pattern applies to iterative test generation: create test 1 → verify it runs → create test 2 → verify → etc.

If stop_reason is "max_tokens", the tool call JSON may be truncated mid-way. You must retry with higher max_tokens. Note: "pause_turn" means the server-side loop hit its iteration cap (default 10) — send the response back to continue.

Hub-and-Spoke Pattern

  • Coordinator (Hub): Receives request, breaks into subtasks, delegates, aggregates results
  • Subagents (Spokes): Specialized for specific task types, run in isolated context, return results to coordinator
  • Subagents have NO shared memory — coordinator owns the state
  • Each subagent is an independent API call

Parallel Spawning

  • Emit multiple Task tool calls in a single response for parallel spawning
  • Independent subtasks run concurrently, not sequentially
  • Example: billing lookup + returns lookup for same customer can run in parallel

Why Separate Subagents?

  • Testable: Each step can be tested independently
  • Retryable: Failed step can be retried without re-running everything
  • Replaceable: Swap out implementations without affecting others
  • Context isolation: Classification errors don't contaminate the draft
  • One giant prompt that does everything breaks down in production

Root Cause Tracing

  • When multi-agent pipelines fail, trace failures to root cause
  • Decomposition failure: Coordinator broke the task into wrong subtasks
  • Execution failure: Subagent failed on a correctly decomposed subtask
  • The fix differs: redesign routing vs. fix individual agent

Scenario in Practice

Multi-Agent Research System: The coordinator receives a research query and delegates to specialized subagents: a search agent finds relevant sources, an analyze agent extracts key findings, a synthesize agent combines results, and a report agent formats the final output. Each subagent runs in isolation with its own API call — the coordinator aggregates all results and handles failures at each stage independently.

Claude Code for CI: In a code review pipeline, the coordinator uses prompt chaining to run a fixed sequence: style check, then security scan, then documentation review. Each step is a separate subagent, and the output of one feeds into the next. Since the workflow is the same for every PR, prompt chaining is preferred over dynamic orchestration.

Subagents do NOT automatically inherit parent context, conversation history, or tool access. You must explicitly pass all necessary information. For parallel work, emit multiple Task tool calls in one response.

Task Decomposition Patterns

PatternHow It WorksUse When
Prompt ChainingSequential steps: output of step N feeds into step N+1Fixed, same workflow every time (e.g., style → security → docs review)
Orchestrator-WorkersCoordinator dynamically decides which workers to invokeVariable tasks requiring dynamic routing
RoutingClassify first, then route to specialized handlerInput types need different handling
ParallelizationFan out independent subtasks simultaneouslyIndependent work (billing + returns for same customer)
Dynamic DecompositionGenerate subtasks based on discoveries at each stepInvestigation tasks (tracing a 500 error through routing → middleware → DB)
For a fixed, repeatable workflow (same 3 checks on every PR), use prompt chaining. For investigation tasks where each finding changes the plan, use dynamic task decomposition.

fork_session

  • Creates independent branches from an existing session context
  • Each fork preserves the prior analysis but explores a different direction
  • Avoids context pollution between alternative approaches
  • Use case: Engineer identified two refactoring approaches — fork to explore each independently

1.3 — Context Passing & Typed Objects

Explicit vs. Implicit Context

Problem: Implicit assumptions produce wrong answers. When context travels between agents, every handoff must be explicit.

  • Structured context is passed explicitly via typed objects (e.g., TicketContext)
  • Each field has a clear meaning and type
  • No ambiguity about what was passed
@dataclass
class TicketContext:
    ticket_text: str
    product_area: str | None = None
    severity: str | None = None
    intent: str | None = None
    customer_tier: str | None = None

Context Passing Patterns

Pattern 1: Coordinator Summary

Pass the coordinator's summary of subagent findings in the Task tool call

Pattern 2: Chain Results

Chain subagent calls: first get results, then invoke next agent with those results as context

Anti-Patterns

  • Having subagent query shared DB (fragile coupling)
  • Having synthesis agent call search tools directly (wrong separation)
  • Assuming subagent inherits parent context

Scenario in Practice

Code Generation with Claude Code: When a team uses Claude Code for refactoring across multiple files, the coordinator passes a typed RefactorContext object containing the target function signature, affected file paths, and coding standards. Without this explicit context, a subagent tasked with updating tests would not know what changed in the source files — it cannot read the coordinator's conversation history.

Developer Productivity with Claude: When an agent helps explore a codebase, the coordinator summarizes findings from a search subagent into a structured CodebaseContext object before passing it to the code generation subagent. Relying on the generation agent to query a shared database for search results would create fragile coupling — an anti-pattern.

Subagents do NOT inherit parent context automatically. The coordinator must explicitly pass customer context and available tools to each subagent.

1.4 — Step Enforcement & Programmatic Gates

Why Gates?

Prompt instructions alone are unreliable under load. Code enforces order; prompts suggest it.

  • Programmatic gates block downstream steps until upstream steps produce verified results
  • Example: process_refund should NOT run until get_customer and lookup_order complete

Enforcement Mechanisms

MechanismBest For
PostToolUse HookValidate whether prerequisite tools were called before allowing a protected tool
allowedToolsRestrict which tools a subagent can access
tool_choiceForce specific tool for a specific turn
Orchestration codePre-configured pipeline that runs steps in sequence
Agent SDK HooksIntercept tool calls for data normalization & validation at the SDK level

Programmatic vs. Prompt-Based Enforcement

ApproachReliabilityWhen to Use
Programmatic (hooks, gates, allowedTools)Deterministic, 0% failureCompliance, security, financial ops
Prompt-based (system prompt rules)Probabilistic, can be bypassedNon-critical preferences

Agent SDK Hooks

Use Agent SDK hooks for tool call interception and data normalization. These run at the SDK layer, giving you programmatic control over every tool invocation — validate inputs, transform outputs, enforce sequencing, or inject metadata before the tool executes.

Refinement Loop Limits

Set a hard iteration limit (e.g., max 3 rounds) to control costs and latency. Unlimited iteration is impractical; adaptive stopping is complex to implement reliably.

Scenario in Practice

Customer Support Resolution Agent: A PostToolUse hook enforces that process_refund cannot execute unless get_customer and lookup_order have already been called in the current session. If the agent tries to skip straight to refund processing, the hook blocks the call and returns an error — no amount of prompt engineering can bypass this programmatic gate.

Structured Data Extraction: After extracting fields from an unstructured document, a programmatic gate validates the output against a JSON schema before allowing downstream processing. If required fields like invoice_number or total_amount are missing, the gate blocks the pipeline and forces a retry — this is enforced in code via allowedTools, not by asking the model to "please validate first."

Tamper-Proof Enforcement Inside the Tool

For business rules like "reimbursements > $500 require manager approval", the most tamper-proof approach is enforcement within the tool itself:

  • The process_reimbursement tool checks the amount internally: ≤$500 auto-disburses, >$500 creates a pending approval request
  • This cannot be bypassed by prompt manipulation, agent reasoning, or parameter tampering
  • Contrast with weaker approaches: Separate tools with prompt instructions (probabilistic), boolean parameters the agent sets (falsifiable), PreToolUse hooks (external enforcement)
Hierarchy of enforcement reliability: Tool-internal logic > PreToolUse hooks > allowedTools restriction > System prompt instructions. For the exam, "tamper-proof" = enforcement in code that the agent cannot influence.
When the exam asks about "most reliable enforcement" for tool ordering, choose PostToolUse hooks or orchestration code over system prompt rules. Prompts suggest; code enforces. Programmatic = 0% failure; prompts = probabilistic. Agent SDK hooks provide interception at the SDK level.

Agent SDK Hooks for Data Normalization

PostToolUse hooks can normalize heterogeneous data formats from different MCP tools before the agent processes them:

Normalization Examples

  • Timestamps: Unix epoch → ISO 8601
  • Status codes: Numeric 200 → "success"
  • Currency: "$1,234.56" → 1234.56
  • Dates: "03/15/2024" → "2024-03-15"

Compliance Interception

  • Block outgoing tool calls that violate compliance rules (e.g., refunds exceeding $500)
  • Redirect blocked actions to alternative workflows (e.g., human escalation)
  • Choose hooks over prompts when business rules require guaranteed compliance

2.1 — Tool Interfaces & Selection Reliability

The model never sees your tool implementation. It chooses a tool from three things only: name, description, and parameter schema.

Strong vs. Weak Tool Interfaces

LeverWeakStrong
Namesearch, lookupsearch_products, get_order_status (object + action)
Description"Search for stuff in the system."Says when to use it AND when NOT to (explicitly defers to sibling tool)
Parametersq: stringorder_id typed with regex pattern ^NP-[0-9]{6}$

Best Practices for Tool Definitions

  • 3-4+ sentence descriptions that explain what, when, when-NOT-to-use, and caveats
  • Strong descriptions specify: what it does, input formats, example queries, boundaries vs. similar tools
  • Typed, specific parameters with regex patterns where applicable
  • Meaningful namespacing: prefix with service (github_list_prs)
  • High-signal responses: Return only fields Claude needs for next step
  • Selection reliability is an interface problem, not a model-size problem
  • Scope each subagent to 4–5 tools relevant to its role — never give all agents access to all tools

One Tool vs. Separate Tools

ApproachWhen to UseExample
Separate toolsOperations have different I/O contracts, different use casesextract_data, summarize_content, verify_claim
One tool + operation paramOperations share the same resource/domain, similar I/Odb_admin(op: "list_tables" | "check_integrity")

Split generic tools when their descriptions overlap or when each operation serves a distinct purpose. Keep them combined when they're operations on the same resource with a clear parameter.

When to Split: Invalid Parameter Combinations

If a tool accepts combinations that are semantically invalid (e.g., log_workout accepting "miles" for strength and "reps" for cardio), split it into category-specific tools: log_cardio_workout(duration, distance) and log_strength_workout(sets, reps, weight). Invalid combinations become impossible because the wrong parameter simply doesn't exist on the tool.

Fixing Misrouting

When tool misrouting occurs, improve descriptions FIRST — before adding classifiers, few-shot examples, or other complexity. Descriptions are the #1 lever for selection reliability. Same model, better tools = better selection.

Disambiguating Similar Tools

When two tools overlap (e.g., summarize_content vs. analyze_document), expand descriptions to include:

  • When to use: "Use for generating brief overviews of known documents"
  • When NOT to use: "Do NOT use for detailed analysis — use analyze_document instead"
  • Example queries: "'Give me the gist of this paper' → summarize_content; 'What themes and structure does this paper use?' → analyze_document"

Anti-Patterns

  • Near-identical descriptions for different tools (causes confusion)
  • Giving all agents access to all tools (scope to 4–5 per role)
  • Using Glob for file content search or Grep for file name matching (wrong tool)

Scenario in Practice

In the Customer Support Resolution Agent, tools like get_customer, lookup_order, process_refund, and escalate_to_human each follow the object-action naming pattern with distinct descriptions. If the agent keeps calling lookup_order when it should call get_customer, the fix is to improve the tool descriptions to clarify when each applies, not to add a classifier layer.

In the Multi-Agent Research System, each subagent (search, analyze, synthesize, report) is scoped to only 4-5 tools relevant to its role, preventing the coordinator from accidentally routing a search request to the synthesis agent.

Advanced Tool Interface Patterns

PatternProblem It SolvesExample
Two-Step Confirmation TokenAgent bypasses preview/dry-run steps for destructive operationspreview_remove_member returns impact + single-use token; execute_remove_member requires that token — architecturally impossible to skip preview
ID Lookup PatternAmbiguous parameters (nicknames, date formats) cause wrong-item errorsReplace game_date, home_team, away_team with game_id + a search_games lookup tool returning matching IDs
Rich Confirmation ResponseUsers approve destructive actions without understanding what they approved (tool returns only "OK")Return structured data: cost estimate, target project, resource specifications, impact summary — gives the agent information to present meaningful confirmation details
Two-step confirmation tokens create a cryptographic dependency chain: execute requires a token that only preview produces. This is stronger than prompt instructions, orchestration-layer confirmation, or server-side time-based validation.

allowedTools for Security Scoping

When a subagent works with sensitive documents, use allowedTools to restrict access to only vetted tools:

  • Define allowedTools: ["analyze_document"] with explicit read permissions and access logging
  • This is a hard boundary — the subagent literally cannot call tools outside this list
  • Do NOT grant access to all tools and trust the subagent to decide what's appropriate
  • MCP server scoping restricts which servers connect; allowedTools restricts which tools within those servers are callable
When misrouting occurs, fix tool descriptions first before building classifiers or adding examples. Scope each subagent to 4–5 relevant tools, not the full toolkit.

2.2 — Structured Errors & Retry Logic

Return Failures as Data, Never Exceptions

# Structured error envelope — transient failure
{
    "isError": True,
    "errorCategory": "transient",  # transient | validation | permission
    "isRetryable": True,
    "content": "Service timeout after 30s"
}

# Business rule violation — non-retryable with customer-friendly message
{
    "isError": True,
    "errorCategory": "permission",
    "isRetryable": False,
    "content": "Refund window expired (45-day policy)",
    "customerMessage": "This order is past the 45-day refund window. I can help you with a store credit instead."
}

The envelope lets the loop retry transient errors and stop on permanent ones. The errorCategory (transient/validation/permission) tells the agent what kind of failure occurred, while isRetryable tells it whether to retry. For business rule violations, include a customerMessage so the agent can communicate appropriately.

Retry Logic Pattern

MAX_RETRIES = 3
for attempt in range(MAX_RETRIES):
    result = call_tool(input)
    if not result.get("isError"):
        return result  # Success
    if not result.get("isRetryable"):
        return result  # Permanent failure, stop
    # Transient failure, retry with backoff
    time.sleep(2 ** attempt)
return {"isError": True, "content": "Max retries exceeded"}

Key Distinction

ScenarioerrorCategoryisErrorisRetryable
Timeout / 503transientTrueTrue
Invalid input formatvalidationTrueFalse
Refund window expiredpermissionTrueFalse
404 Not FoundvalidationTrueFalse
No results found—FalseN/A

Scenario in Practice

In the Structured Data Extraction scenario, when the extraction tool hits a timeout calling a validation API, the error envelope returns {"isError": true, "errorCategory": "transient", "isRetryable": true}, and the agent retries with exponential backoff. But when a document fails JSON schema validation, it returns "errorCategory": "validation" with "isRetryable": false, so the agent stops and reports the specific field mismatch instead of retrying endlessly.

Internal Retry vs. Exposing isRetryable

Not all retries should be exposed to the agent. The most effective pattern handles each error type at the appropriate level:

Error TypeHandlingAgent Sees
Network timeouts (transient)Automatic retry inside the tool with backoffNothing — tool succeeds transparently
Malformed parameters (permanent)Return immediately with validation detailsisError: true + parameter fix guidance

This avoids burdening the agent with retry decisions for transient errors it can't influence. Only surface errors the agent can act on (e.g., fixing malformed parameters).

"No data found" is NOT an error — it's a valid empty result (isError: false). A timeout IS an error that should be retried.

2.3 — tool_choice & Selection Control

tool_choice Options

ValueBehaviorUse Case
autoClaude decides whether to call any tools or respond directlyDefault; most flexible
anyClaude MUST use one of the provided tools (but picks which)Force tool use without specifying which
{"type":"tool","name":"X"}Claude MUST use the specified toolDeterministic classification step
noneClaude cannot use any toolsPrevent all tool use

When to Use Each

  • auto: General conversation, agent decides whether to call tools or respond with text
  • any: Guarantee structured output — model MUST call a tool. Use when you have multiple extraction schemas and don't know the document type in advance
  • Forced tool: Deterministic step — always call a specific named tool (e.g., force extract_metadata before enrichment)
  • none: Pure text response needed

Important Limitations

  • With any or tool: No natural language before tool_use blocks (prefills assistant message)
  • Manual extended thinking: Only supports auto and none
  • Adaptive thinking: Supports ALL tool_choice values
  • Changing tool_choice invalidates cached message blocks

Scenario in Practice

In Claude Code for Continuous Integration, the PR review pipeline uses tool_choice: {"type":"tool","name":"review_pr"} to force the agent to always produce a structured review rather than sometimes responding with plain text. This guarantees every PR gets a consistent, parseable review object.

In the Structured Data Extraction scenario, tool_choice: "any" is ideal when the agent receives documents of unknown type and must pick the correct extraction schema (invoice vs. receipt vs. contract) -- it guarantees structured output without prescribing which schema to use.

Forcing the classifier tool with tool_choice: {"type":"tool","name":"classify"} makes triage deterministic — always exactly one classification per ticket.

Scenario in Practice

In Developer Productivity with Claude, instead of writing custom Bash scripts to query the GitHub API via curl, the team configures a GitHub MCP server in .mcp.json so the agent can call mcp__github__list_prs directly. Credentials are stored as environment variable references ("token": "$GITHUB_TOKEN"), not hardcoded in the config file.

For Code Generation with Claude Code, the built-in incremental exploration pattern (Glob -> Grep -> Read -> Edit) lets the agent understand existing code structure before generating new code, avoiding conflicts with existing implementations.

Use existing MCP servers (e.g., Jira) rather than building custom ones or using raw curl. MCP gives the agent data directly without copy-paste. Evaluate community MCP servers before building custom ones.

MCP Resources (Content Catalogs)

  • MCP resources expose read-only content catalogs (issue summaries, documentation hierarchies, database schemas) to give agents visibility into available data without exploratory tool calls
  • Resources reduce the "discovery problem" — the agent can browse what's available before making targeted tool calls
  • Example: A Jira MCP server might expose a resource listing all project keys and issue types, so the agent knows what to query

MCP Credential Security

  • Use environment variable expansion in .mcp.json: "password": "$DB_PASSWORD"
  • Version-control .mcp.json with variable references, NOT hardcoded credentials
  • Each developer sets actual values via their local environment

2.5 — Built-in Tool Best Practices & Recovery

Tool Selection Decision Tree

NeedUseNOT
Read file contentsReadBash cat/head/tail
Edit existing fileEditBash sed/awk
Create new fileWriteBash echo >
Search content in filesGrepBash grep
Find files by nameGlobBash find
Run build/test commandsBash—
Run language analysisBash—
Validate generated filesGlob + Read + BashAny single tool alone
Prefer dedicated tools over Bash. Use Bash only for shell-specific operations (running tests, build tools, git commands).

Validating Generated Code Files

After generating boilerplate, use all three: Glob to verify naming/placement, Read to inspect content, Bash to run linters. Each validates a different dimension.

Error Recovery Strategies

Edit Tool: "old_string not unique"

  1. First: Try Edit again with a larger substring including more surrounding context to make the match unique
  2. Fallback: Read the file, then use Write for a complete rewrite (last resort)
  3. Never: Use Bash sed or ask user to edit manually

Edit Fallback: Read → Write

When Edit fails on repetitive patterns (non-unique old_string), use: Read the file → modify content in memory → Write the full updated file.

Multi-File Changes: Loop Pattern

For repetitive changes across many files (e.g., updating an API endpoint in 20 services): Loop: Read each file → Edit the content → Read back to verify. Never use Bash find-and-replace across all files at once.

Iterative Refactoring (Large Functions)

For refactoring a 200-line function: use multiple small Edit operations, testing after each change. If a test fails, you know exactly which edit caused it. Don't refactor everything in one Write — it makes debugging impossible.

Post-Write Verification

  • After using Write, always Read the file back to verify content matches expectations
  • Especially critical for generated code (migrations, configs)

Understanding Legacy Code

  • For old files: use Grep to find test files or docs that reference the module
  • Tests show how it's used; docs explain why it exists

Scenario in Practice

In Claude Code for Continuous Integration, the automated review agent uses Grep to search for test coverage patterns and Read to inspect flagged files -- never Bash cat. When the Edit tool returns an "old_string not unique" error while applying a suggested fix, the agent recovers by including more surrounding context to make the match unique, rather than falling back to Bash sed.

In the Code Generation with Claude Code scenario, after generating a new utility file with Write, the agent always calls Read to verify the written content matches expectations before proceeding to integration.

Grep Patterns for Function Usage

To find all usages of a function, run all three searches:

grep functionName
+
grep functionName(
+
grep import.*functionName

Name (declarations/references) + Calls (invocations) + Imports (usage patterns)

When a function is re-exported under aliases via wrapper modules, first read the wrappers to identify all exposed names, then Grep for each name across the codebase.

4.1 — Explicit Criteria & Precision Prompting

Vague vs. Explicit Prompts

Vague: "Decide the moderation action: remove, review, or allow."
Explicit: 
Choose the action using these exact definitions:
- REMOVE: clear, unambiguous violation - doxxing,
  credible threat, clearly illegal content.
- REVIEW: may violate policy but needs a human -
  likely spam, borderline harassment.
- ALLOW: rude/blunt/off-topic but not a violation.

Tie-break: when unsure between REMOVE and REVIEW,
choose REVIEW.

Why This Matters

  • Vague "remove" leaves the label undefined — model over-fires, creating false positives
  • Explicit criteria + tie-break rule pull false positives back down on the same model
  • Three layers of precision:
    1. Criteria fix the decision (what each label means)
    2. Few-shot examples fix the format (exact output shape)
    3. Principles fix the intent (how to generalize)

Reducing False Positives in Practice

  • Temporarily disable high false-positive categories while you refine their criteria with concrete examples — this restores developer trust faster than tuning confidence thresholds
  • Define specific review criteria per category (bugs, security, style) rather than relying on confidence-based filtering
  • Use "be conservative" or "only report high-confidence findings" as a last resort — specific categorical criteria outperform vague directives

Scenario in Practice

Claude Code for CI (Scenario 5): A team configures automated code reviews but gets flooded with false-positive style warnings. Instead of lowering a generic confidence threshold, they define explicit criteria per category — e.g., "flag unused imports only if the import is not referenced within 10 lines of a conditional block" — and add a tie-break rule: "when uncertain whether a finding is a bug or a style issue, classify as style and do not block the PR."

Customer Support Agent (Scenario 1): The support agent's escalate_to_human tool fires too often on frustrated but routine complaints. Adding explicit criteria — "escalate only when the customer explicitly requests a manager, threatens legal action, or the issue involves a policy gap" — reduces unnecessary escalations without missing genuine cases.

Define each label with concrete, testable boundaries before applying it. Include a tie-break rule for ambiguous cases. When a category generates too many false positives, disable it temporarily while refining criteria rather than lowering confidence thresholds.

Tool Schema for Structured Output

Use tool definitions to force Claude to return structured data:

  "name": "classify_content",
  "description": "Classify content moderation action",
  "input_schema": {
    "type": "object",
    "properties": {
      "action": {
        "type": "string",

      },
      "rationale": {
        "type": "string",

        "type": "number",

# Force this specific tool

Validation & Retry Loop

MAX_RETRIES = 3
for attempt in range(MAX_RETRIES):
    response = client.messages.create(
        tools=tools,
        tool_choice={"type":"tool","name":"classify"},
        messages=messages
    )
    result = response.content[0].input

    # Validate
    if validate_schema(result):

    # Add error feedback and retry
    messages.append({"role":"user","content":

    })

raise ValueError("Failed after retries")

Key Pattern

  • Use tool schema to define expected output
  • Force tool with tool_choice
  • Validate result against schema
  • Retry with error feedback if invalid

Schema Design: Nullable Fields & Limitations

Make Fields Nullable

When source documents may lack information, make fields nullable to prevent fabrication:

"birthdate": {
  "type": ["string", "null"],
  "description": "ISO date or null if not found"
}

Without null option, Claude may hallucinate a value rather than admit it's missing.

Enum "unclear" + "other" Patterns

  • Add "unclear" enum values for ambiguous cases — prevents forcing a wrong classification
  • Add "other" + detail string field for extensible categories the schema didn't anticipate
  • Include format normalization rules in prompts alongside strict schemas to handle inconsistent source formatting

JSON Schema Limitations

JSON schemas with tool_use eliminate syntax errors (malformed JSON, missing fields) but do NOT prevent semantic errors (wrong values, hallucinated data, incorrect classifications). You still need validation logic to check semantic correctness.

4.4 — Batch API & Multipass Processing

Message Batches API

  • 50% cost reduction on ALL token types (input, output, cache reads, cache writes, thinking)
  • Up to 100,000 requests or 256 MB per batch
  • SLA: 24 hours (practice: typically 5-30 min)
  • Each request processed independently
  • Failure of one request does NOT affect others
  • Order NOT guaranteed — use meaningful custom_id
  • Stacks with prompt caching: 50% batch + 90% cache = up to 95% savings

Limitations

  • No multi-turn tool calling within a single batch request (cannot execute tools mid-request and return results)
  • Use custom_id fields to correlate batch request/response pairs
  • Calculate submission frequency based on SLA: e.g., 4-hour windows to guarantee 30-hour total SLA with 24-hour processing

Use Cases

  • Large-scale evaluations, overnight reports, nightly test generation
  • Content moderation at scale, weekly audits
  • NOT for real-time interactions or blocking pre-merge checks

Multipass Pattern

Run Claude over the same input multiple times and compare/aggregate results:

# Pass 1: Initial classification
result1 = classify(content)

# Pass 2: Verification with different prompt
result2 = verify(content, result1)

# Pass 3: Confidence calibration
if result1 != result2:
    result3 = arbitrate(content, result1, result2)
    final = result3
else:
    final = result1  # High confidence

When to Use Multipass

  • High-stakes decisions (moderation, medical)
  • When single-pass accuracy isn't sufficient
  • Combine with batching for cost efficiency
Keep blocking pre-merge checks synchronous — do NOT route them through the Batch API. Batch API has a 24-hour SLA and is for latency-tolerant workflows only. A CI check that blocks a merge must return a result immediately.

Scenario in Practice

Multi-Agent Research System (Scenario 3): The coordinator queues all subagent tasks — search, analyze, synthesize — as a single Message Batch to get 50% cost savings. Since each subagent request is independent, batch processing is ideal. Results are correlated using custom_id fields like "search-q1" and "analyze-q1", then fed to the report subagent synchronously.

Claude Code for CI (Scenario 5): Nightly test generation across 200 source files uses the Batch API for cost efficiency. However, pre-merge code review checks remain synchronous — routing them through the Batch API would block PRs for up to 24 hours, violating the team's merge SLA.

Batch API gives 50% cost savings and stacks with caching for up to 95% savings. But never batch time-sensitive operations like pre-merge CI checks — those must be synchronous.

4.5 — Temperature & Sampling Parameters

Temperature

  • Range: 0.0 – 1.0 for Claude (OpenAI uses 0–2.0)
  • Default: 1.0 (maximum randomness by default)
  • Controls randomness via softmax scaling of token logits
  • Low (0.0–0.3): Classification, data extraction, code generation, math
  • High (0.7–1.0): Creative writing, brainstorming, diverse outputs
  • → temperature: 0 does NOT guarantee deterministic output (floating-point math, MoE architecture)

top_p & top_k

  • top_p (nucleus sampling): considers tokens whose cumulative probability ≤ p
  • top_k: NOT available in native Claude API (only via Vertex AI / Bedrock)
  • → Alter temperature OR top_p, NOT both simultaneously

Deprecation (Opus 4.7+)

  • Temperature is deprecated on Claude Opus 4.7+
  • Replaced by effort parameter: low | medium | high
# Low temperature — precise, factual tasks
response = client.messages.create(
    model="claude-sonnet-4-6",
    temperature=0.0,
    messages=[{"role": "user", "content": "Extract the date: 'Meeting on Jan 15'"}]
)

# High temperature — creative, diverse outputs
response = client.messages.create(
    model="claude-sonnet-4-6",
    temperature=0.9,
    messages=[{"role": "user", "content": "Write a tagline for a coffee brand"}]
)

Scenario in Practice

Structured Data Extraction (Scenario 6): When extracting dates, amounts, and names from legal contracts, use temperature: 0.0 for maximum precision — creative variation in extracted data is never desirable. The low temperature ensures consistent, deterministic-like output across repeated extractions of the same document.

Developer Productivity (Scenario 4): When Claude helps brainstorm alternative API designs, use temperature: 0.8-1.0 for diverse suggestions. But when generating the final implementation code, switch to temperature: 0.0. Remember: even at temperature: 0, output is not guaranteed deterministic due to floating-point math and model architecture.

5.1 — Context Preservation & Optimization

The Problem

Long conversations lose details (numbers, dates, IDs). After auto-compact, nuance disappears.

Progressive summarization silently corrupts transactional data — amounts, dates, order numbers become vague paraphrases. Never use progressive summarization on conversations with transactional data. Instead, extract specifics into a persistent case facts block.

Case Facts Block

A persistent structured block that keeps critical details alive across turns:

# CASE FACTS (do not remove)
- Customer: Jane Doe (ID: CUST-4421)
- Order: NP-100190
- Issue: Return request for boots
- Account Tier: Enterprise
- SLA: 4-hour response
  • Place at start or end of context (primacy/recency effect)
  • Write to file to survive /compact
  • Keep it small and high-signal
  • Include case facts verbatim in every prompt — never summarize them

Trimming Tool Outputs

  • Summarize a 500-row query into the 5 relevant fields
  • Return only fields Claude needs for next step
  • Use semantic identifiers (slugs, UUIDs) not opaque refs
  • MCP output limit: 25,000 tokens (warning at 10,000)

Context Placement

PositionEffect
Start of contextPrimacy effect — high recall
End of contextRecency effect — high recall
Middle of context"Lost in the middle" — lower recall
Place key summaries/findings at the beginning of long inputs to combat the "lost in the middle" effect.

Scenario in Practice

Code Generation with Claude Code: A team uses Claude Code for a multi-file refactoring session. After 30+ turns, auto-compaction fires and the original function signatures being refactored become vague ("the function we discussed"). To prevent this, the developer writes a case facts block to a scratchpad file listing the exact function names, file paths, and the target API contract — ensuring these specifics survive /compact and remain available verbatim in later turns.

Keep critical info at the start or end of context (primacy/recency). Write case facts to a file so they survive /compact. Never summarize transactional data — include verbatim.

Meanwhile, the analyze subagent queries a database and gets zero results. This is not an error — it returns {"isError": false, "results": []} so the pipeline continues with a gap annotation rather than terminating.

A timeout is an infrastructure error (retry). "No data found" is a valid result (don't retry). Subagents should silently retry transient errors; only propagate unresolved failures. Never terminate the entire pipeline on a single tool failure — degrade gracefully and annotate gaps.

5.4 — Large Codebase Exploration & Session Management

Strategies for Long Sessions

  • Scratchpad files: Write findings to disk so they survive compaction
  • Subagents: Isolate exploration to prevent context flood
  • /compact: Manually trim context. Run at ~60% capacity, not 95%. Accepts custom prompt for targeted curation
  • State export: Save progress for crash recovery

Exploration Strategy

Grep entry points

Don't read everything. Use targeted search, then incremental reads.

Crash Recovery — --resume vs --continue

FlagBehaviorUse When
--resume <id>Resume specific session by IDCI/CD, automation (capture from session_id)
--continueResume most recent session in current directoryDaily focused work on single project

Sessions stored at ~/.claude/projects/ as JSONL.

Resume trade-off: Resuming loads the full prior conversation into context. If the prior session was long, you start with most of the context budget used. A fresh session with a summary gives a clean context window.

Resuming with Changed Files

When resuming a session where source files changed overnight, inform the agent which specific files changed for targeted reanalysis — don't re-read everything (wasteful) or ignore changes (stale analysis).

Context Overflow & Hallucinations

When a review session grows very large and starts hallucinating, start a fresh session with a summary of prior findings rather than continuing the stale session. Don't use --resume when the accumulated context is the problem.

Scenario in Practice

Developer Productivity with Claude: A developer uses Claude Code to explore a large monorepo with 500+ files. After reading dozens of files, context reaches ~60% capacity. Rather than waiting for auto-compaction to silently drop details, they run /compact with a targeted prompt: "Keep all findings about the auth module and database schema." They also write key architectural notes to a scratchpad file so discoveries persist even if the session crashes and is resumed with --continue.

When context degrades (generic responses instead of specifics), summarize findings, then spawn a subagent for the next exploration with that summary as initial context.

5.5 — Human Review & Confidence Calibration

Confidence-Based Routing

def route_decision(result, threshold=70):
    if result["confidence"] >= threshold:
        return auto_approve(result)
    else:
        return request_human_review(result)

# Per-field confidence
{
  "name":     {"value": "John Doe", "confidence": 95},
  "birthdate":{"value": "1985-03-15","confidence": 60},
  "address":  {"value": "123 Main St","confidence": 40}
}
# Only review low-confidence fields

Calibrating with a Labeled Validation Set

Don't trust raw confidence scores — calibrate them against a labeled validation set of human-verified extractions.

  • Build a labeled dataset with known-correct extractions across document types
  • Compare model confidence scores against actual accuracy on this set
  • Set review thresholds based on measured precision, not assumed confidence
  • Re-calibrate periodically as document types and extraction patterns change

Evaluation Tiers

90-100Auto-approve, spot-check 5%
70-89Light review, sample 20%
50-69Full human review
<50Always escalate to human

Independent Review > Self-Review

A separate Claude instance with fresh context catches errors that self-review misses. The same instance reviewing its own output tends to rationalize its original errors rather than finding them. Always use an independent reviewer for high-stakes outputs.
  • Self-review: Same context, same biases — rationalized errors persist
  • Independent review: Fresh context, no prior commitment — catches actual mistakes
  • Implement as: spawn a new API call with only the output to review (no conversation history)

Multi-Pass Review Architecture

  • Per-file local passes: Analyze each file individually for local issues (bugs, style, security)
  • Cross-file integration pass: Separate pass examining data flow and dependencies across files
  • Verification pass: Model self-reports confidence alongside each finding for calibrated routing
  • Validate accuracy per document type and per field before automating high-confidence extractions

Accuracy Monitoring Over Time

Extraction accuracy can degrade silently as document formats evolve:

  • Track confidence trends continuously — if average confidence drops, investigate immediately
  • A gradual decline signals format drift; a sudden drop signals a breaking change
  • Quarterly full re-testing (B) is too slow; manual sampling (D) is too sparse
  • Automated trend monitoring catches problems between manual audits

Segment-Level Validation Before Automation

Before automating high-confidence extractions, aggregate accuracy can mask segment-level failures:

  • A system 98% accurate overall might be only 60% accurate on a specific document type or field
  • Analyze accuracy by document type AND field to confirm consistency across all segments
  • Only then set confidence thresholds for automation
Building trust with CI/automation: Start with a small set of high-confidence checks and expand gradually as accuracy builds trust. Don't deploy all checks at once — early wins with precise findings establish credibility.

Scenario in Practice

Structured Data Extraction: An extraction pipeline processes medical invoices. The model extracts "name" with 95% confidence but "address" at only 40%. Instead of sending the entire document for human review, the system uses per-field confidence routing — auto-approving high-confidence fields and flagging only "address" for human verification, reducing reviewer workload by 70%.

Claude Code for CI: During automated code review, a separate Claude instance with fresh context reviews the PR diff independently. This avoids the self-review trap where the same instance rationalizes its original suggestions instead of catching real issues.

5.6 — Information Provenance & Uncertainty Handling

Claim-Source Mapping

Map every claim to its source (URL, doc name, evidence excerpt).

{
  "claim": "30-day return window applies",
  "sources": [
    {
      "document": "returns-policy.md",
      "excerpt": "Items may be returned within 30 days",
      "publication_date": "2024-01-15"
    }
  ],
  "confidence": 95,
  "status": "confirmed"
}

Citation Types

  • document_citation — From uploaded documents
  • web_search_result_location_citation — From web search
  • Always include quoted_text for verification

Hallucination Detection: required_evidence

When models hallucinate data (e.g., dates not in the source), add a required_evidence field to the schema forcing the model to cite where each value appears in the source document. Values without evidence are flagged as potential hallucinations.

Handling Conflicting Sources

  • Keep conflicting info from multiple sources — don't pick one
  • Always include publication dates for temporal context
  • Flag where sources disagree for reviewer attention

Confirmed vs. Contested Report

## Confirmed Findings
- 30-day return window [Source A, Source B]
- Free shipping over $50 [Source A]

## Contested Findings
- Refund processing time:
  - Source A (2024-06): "3-5 business days"
  - Source B (2023-11): "7-10 business days"
  - Note: Source A is more recent

## Unverified (Single Source)
- Holiday return extension [Source C only]

Temporal Data & Coverage Annotations

  • Require publication/collection dates in structured outputs to prevent temporal differences from being misinterpreted as contradictions
  • Render different content types appropriately: financial data as tables, news as prose, technical findings as structured lists
  • Structure synthesis output with coverage annotations indicating which findings are well-supported vs. which have gaps due to unavailable sources
  • Require subagents to include metadata (dates, source locations, methodological context) in structured outputs for accurate downstream synthesis

Scenario in Practice

Multi-Agent Research System: The coordinator delegates a market analysis to search and analyze subagents. The search subagent returns two sources with conflicting revenue figures — one from Q1 2024 and another from Q3 2023. Rather than silently picking the newer source, the synthesize subagent classifies this as a contested finding, includes both figures with their publication dates, and adds a coverage annotation noting that no Q4 data was available.

Never silently pick one conflicting source. Present both with publication dates and let the reviewer decide. Distinguish confirmed, contested, and single-source claims. Always require temporal context in structured outputs.
