1.1 — The Agentic Loop & stop_reason

An agentic loop is NOT a for-loop with a fixed iteration count. It runs until Claude says it is done. The mechanism is stop_reason.

stop_reason Values

ValueMeaningYour Code Does
"tool_use"Claude wants to invoke a toolExecute the tool, append result as user message, loop again
"end_turn"Claude finished its responseExtract text from content[], break out of loop
"max_tokens"Response cut at token limitLog warning; consider summarizing and retrying
"stop_sequence"Custom stop string matchedTreat as end_turn unless you have specific logic
"pause_turn"Server-side iteration limit reached (default 10)Send assistant response back to continue processing
"refusal"Claude declined to respondHandle refusal, possibly rephrase request

The Loop Pattern

response = client.messages.create(
    model="claude-sonnet-4-6",
    messages=messages,
    tools=tools
)

while response.stop_reason == "tool_use":
    # Extract tool_use blocks from response
    tool_block = response.content[i]  # type: tool_use
    # Execute tool externally
    result = execute_tool(tool_block.name, tool_block.input)
    # Append assistant msg + tool_result to messages
    messages.append({"role":"assistant","content":response.content})
    messages.append({"role":"user","content":[{
        "type":"tool_result",
        "tool_use_id": tool_block.id,
        "content": result
    }]})
    # Loop again
    response = client.messages.create(..., messages=messages)
The agentic loop checks stop_reason, NOT a fixed iteration count or natural language like "I'm done". Tool results are appended back as user messages with tool_result blocks. Checking response text for "done" is an anti-pattern.
If stop_reason is "max_tokens", the tool call JSON may be truncated mid-way. You must retry with higher max_tokens. Note: "pause_turn" means the server-side loop hit its iteration cap (default 10) — send the response back to continue.

Hub-and-Spoke Pattern

  • Coordinator (Hub): Receives request, breaks into subtasks, delegates, aggregates results
  • Subagents (Spokes): Specialized for specific task types, run in isolated context, return results to coordinator
  • Subagents have NO shared memory — coordinator owns the state
  • Each subagent is an independent API call

Parallel Spawning

  • Emit multiple Task tool calls in a single response for parallel spawning
  • Independent subtasks run concurrently, not sequentially
  • Example: billing lookup + returns lookup for same customer can run in parallel

Why Separate Subagents?

  • Testable: Each step can be tested independently
  • Retryable: Failed step can be retried without re-running everything
  • Replaceable: Swap out implementations without affecting others
  • Context isolation: Classification errors don't contaminate the draft
  • One giant prompt that does everything breaks down in production

Root Cause Tracing

  • When multi-agent pipelines fail, trace failures to root cause
  • Decomposition failure: Coordinator broke the task into wrong subtasks
  • Execution failure: Subagent failed on a correctly decomposed subtask
  • The fix differs: redesign routing vs. fix individual agent
Subagents do NOT automatically inherit parent context, conversation history, or tool access. You must explicitly pass all necessary information. For parallel work, emit multiple Task tool calls in one response.

Task Decomposition Patterns

PatternHow It WorksUse When
Prompt ChainingSequential steps: output of step N feeds into step N+1Fixed, same workflow every time (e.g., style → security → docs review)
Orchestrator-WorkersCoordinator dynamically decides which workers to invokeVariable tasks requiring dynamic routing
RoutingClassify first, then route to specialized handlerInput types need different handling
ParallelizationFan out independent subtasks simultaneouslyIndependent work (billing + returns for same customer)
For a fixed, repeatable workflow (same 3 checks on every PR), use prompt chaining. For dynamic routing, use orchestrator-workers.

fork_session

  • Creates independent branches from an existing session context
  • Each fork preserves the prior analysis but explores a different direction
  • Avoids context pollution between alternative approaches
  • Use case: Engineer identified two refactoring approaches — fork to explore each independently

1.3 — Context Passing & Typed Objects

Explicit vs. Implicit Context

Problem: Implicit assumptions produce wrong answers. When context travels between agents, every handoff must be explicit.

  • Structured context is passed explicitly via typed objects (e.g., TicketContext)
  • Each field has a clear meaning and type
  • No ambiguity about what was passed
@dataclass
class TicketContext:
    ticket_text: str
    product_area: str | None = None
    severity: str | None = None
    intent: str | None = None
    customer_tier: str | None = None

Context Passing Patterns

Pattern 1: Coordinator Summary

Pass the coordinator's summary of subagent findings in the Task tool call

Pattern 2: Chain Results

Chain subagent calls: first get results, then invoke next agent with those results as context

Anti-Patterns

  • Having subagent query shared DB (fragile coupling)
  • Having synthesis agent call search tools directly (wrong separation)
  • Assuming subagent inherits parent context
Subagents do NOT inherit parent context automatically. The coordinator must explicitly pass customer context and available tools to each subagent.

1.4 — Step Enforcement & Programmatic Gates

Why Gates?

Prompt instructions alone are unreliable under load. Code enforces order; prompts suggest it.

  • Programmatic gates block downstream steps until upstream steps produce verified results
  • Example: process_refund should NOT run until get_customer and lookup_order complete

Enforcement Mechanisms

MechanismBest For
PostToolUse HookValidate whether prerequisite tools were called before allowing a protected tool
allowedToolsRestrict which tools a subagent can access
tool_choiceForce specific tool for a specific turn
Orchestration codePre-configured pipeline that runs steps in sequence
Agent SDK HooksIntercept tool calls for data normalization & validation at the SDK level

Programmatic vs. Prompt-Based Enforcement

ApproachReliabilityWhen to Use
Programmatic (hooks, gates, allowedTools)Deterministic, 0% failureCompliance, security, financial ops
Prompt-based (system prompt rules)Probabilistic, can be bypassedNon-critical preferences

Agent SDK Hooks

Use Agent SDK hooks for tool call interception and data normalization. These run at the SDK layer, giving you programmatic control over every tool invocation — validate inputs, transform outputs, enforce sequencing, or inject metadata before the tool executes.

Refinement Loop Limits

Set a hard iteration limit (e.g., max 3 rounds) to control costs and latency. Unlimited iteration is impractical; adaptive stopping is complex to implement reliably.

When the exam asks about "most reliable enforcement" for tool ordering, choose PostToolUse hooks or orchestration code over system prompt rules. Prompts suggest; code enforces. Programmatic = 0% failure; prompts = probabilistic. Agent SDK hooks provide interception at the SDK level.

Agent SDK Hooks for Data Normalization

PostToolUse hooks can normalize heterogeneous data formats from different MCP tools before the agent processes them:

Normalization Examples

  • Timestamps: Unix epoch → ISO 8601
  • Status codes: Numeric 200 → "success"
  • Currency: "$1,234.56" → 1234.56
  • Dates: "03/15/2024" → "2024-03-15"

Compliance Interception

  • Block outgoing tool calls that violate compliance rules (e.g., refunds exceeding $500)
  • Redirect blocked actions to alternative workflows (e.g., human escalation)
  • Choose hooks over prompts when business rules require guaranteed compliance

2.1 — Tool Interfaces & Selection Reliability

The model never sees your tool implementation. It chooses a tool from three things only: name, description, and parameter schema.

Strong vs. Weak Tool Interfaces

LeverWeakStrong
Namesearch, lookupsearch_products, get_order_status (object + action)
Description"Search for stuff in the system."Says when to use it AND when NOT to (explicitly defers to sibling tool)
Parametersq: stringorder_id typed with regex pattern ^NP-[0-9]{6}$

Best Practices for Tool Definitions

  • 3-4+ sentence descriptions that explain what, when, when-NOT-to-use, and caveats
  • Strong descriptions specify: what it does, input formats, example queries, boundaries vs. similar tools
  • Typed, specific parameters with regex patterns where applicable
  • Meaningful namespacing: prefix with service (github_list_prs)
  • High-signal responses: Return only fields Claude needs for next step
  • Selection reliability is an interface problem, not a model-size problem
  • Scope each subagent to 4–5 tools relevant to its role — never give all agents access to all tools

Fixing Misrouting

When tool misrouting occurs, improve descriptions FIRST — before adding classifiers, few-shot examples, or other complexity. Descriptions are the #1 lever for selection reliability. Same model, better tools = better selection.

Anti-Patterns

  • Near-identical descriptions for different tools (causes confusion)
  • Giving all agents access to all tools (scope to 4–5 per role)
  • Using Glob for file content search or Grep for file name matching (wrong tool)
When misrouting occurs, fix tool descriptions first before building classifiers or adding examples. Scope each subagent to 4–5 relevant tools, not the full toolkit.

2.2 — Structured Errors & Retry Logic

Return Failures as Data, Never Exceptions

# Structured error envelope
{
    "isError": True,
    "isRetryable": True,   # Transient failure
    "content": "Service timeout after 30s"
}

# vs. permanent failure
{
    "isError": True,
    "isRetryable": False,  # Don't retry
    "content": "Order NP-999999 not found (404)"
}

The envelope lets the loop retry a timeout and stop on a 404 — the model never sees a Python crash.

Retry Logic Pattern

MAX_RETRIES = 3
for attempt in range(MAX_RETRIES):
    result = call_tool(input)
    if not result.get("isError"):
        return result  # Success
    if not result.get("isRetryable"):
        return result  # Permanent failure, stop
    # Transient failure, retry with backoff
    time.sleep(2 ** attempt)
return {"isError": True, "content": "Max retries exceeded"}

Key Distinction

ScenarioisErrorisRetryable
Timeout / 503TrueTrue
404 Not FoundTrueFalse
No results foundFalseN/A
"No data found" is NOT an error — it's a valid empty result (isError: false). A timeout IS an error that should be retried.

2.3 — tool_choice & Selection Control

tool_choice Options

ValueBehaviorUse Case
autoClaude decides whether to call any tools or respond directlyDefault; most flexible
anyClaude MUST use one of the provided tools (but picks which)Force tool use without specifying which
{"type":"tool","name":"X"}Claude MUST use the specified toolDeterministic classification step
noneClaude cannot use any toolsPrevent all tool use

When to Use Each

  • auto: General conversation, agent decides
  • any: Force at least one tool call per turn
  • Forced tool: Deterministic triage/classification — always one clean output
  • none: Pure text response needed

Important Limitations

  • With any or tool: No natural language before tool_use blocks (prefills assistant message)
  • Manual extended thinking: Only supports auto and none
  • Adaptive thinking: Supports ALL tool_choice values
  • Changing tool_choice invalidates cached message blocks
Forcing the classifier tool with tool_choice: {"type":"tool","name":"classify"} makes triage deterministic — always exactly one classification per ticket.

Open-source standard for connecting AI apps to external systems.

Transport Types

Use existing MCP servers (e.g., Jira) rather than building custom ones or using raw curl. MCP gives the agent data directly without copy-paste. Evaluate community MCP servers before building custom ones.

MCP Resources (Content Catalogs)

2.5 — Built-in Tool Best Practices & Recovery

Tool Selection Decision Tree

NeedUseNOT
Read file contentsReadBash cat/head/tail
Edit existing fileEditBash sed/awk
Create new fileWriteBash echo >
Search content in filesGrepBash grep
Find files by nameGlobBash find
Run build/test commandsBash—
Run language analysisBash—
Prefer dedicated tools over Bash. Use Bash only for shell-specific operations (running tests, build tools, git commands).

Error Recovery Strategies

Edit Tool: "old_string not unique"

  1. First: Try Edit again with a larger substring including more surrounding context to make the match unique
  2. Fallback: Read the file, then use Write for a complete rewrite (last resort)
  3. Never: Use Bash sed or ask user to edit manually

Post-Write Verification

  • After using Write, always Read the file back to verify content matches expectations
  • Especially critical for generated code (migrations, configs)

Understanding Legacy Code

  • For old files: use Grep to find test files or docs that reference the module
  • Tests show how it's used; docs explain why it exists

Grep Patterns for Function Usage

To find all usages of a function, run all three searches:

grep functionName
+
grep functionName(
+
grep import.*functionName

Name (declarations/references) + Calls (invocations) + Imports (usage patterns)

When a function is re-exported under aliases via wrapper modules, first read the wrappers to identify all exposed names, then Grep for each name across the codebase.

3.3 — Path-Specific Rules & Conditional Loading

How It Works

Rules in .claude/rules/ with YAML frontmatter + glob patterns load only when paths match.

# .claude/rules/security.md
---
paths:
  - "src/auth/**/*.py"
  - "src/payments/**/*.py"
---

# Security Rules
- Never log credentials or tokens
- All inputs must be sanitized
- Use parameterized queries only
  • Saves tokens (rules load only when relevant)
  • Improves precision (focused instructions)
  • Triggers on file read, not every tool use

Glob Patterns

PatternMatches
**/*.tsAll TypeScript files
src/**/*All files under src/
**/*.test.tsxAll React test files
src/*.{ts,tsx}TS & TSX in src/

Loading Rules

  • No frontmatter = loads at launch (same as CLAUDE.md)
  • With paths: = loads when Claude reads matching files
  • Rules without paths can also be in .claude/rules/ for organization

Rules vs. Directory CLAUDE.md

When coding conventions span many directories (e.g., "all .py files use type hints"), use path-scoped rules in .claude/rules/ with glob frontmatter. A directory-level CLAUDE.md only applies within that specific directory — it won't cover files spread across the codebase.
Path-scoped rules with glob frontmatter save tokens AND improve precision vs. a monolithic CLAUDE.md. Rules load only when Claude reads files matching the pattern. Use rules (not directory CLAUDE.md) when conventions span many directories.

3.5 — Iterative Refinement & CI/CD Integration

Iterative Refinement Techniques

Test-Driven Development (TDD)

  1. Write failing tests first
  2. Ask Claude to make them pass
  3. Iterate until green

Interview-Style Prompting

  • Clarify requirements before execution
  • Ask Claude to propose, then refine
  • Give concrete input/output examples

CI/CD Integration

Headless Mode Flags

# Run in CI pipeline
claude -p "review this PR" \
  --output-format json \
  --max-turns 5

# Pipe content for analysis
git diff HEAD~1 | claude -p "review changes"

Key Flags

-pNon-interactive (headless) mode
--output-format jsonStructured JSON output (print mode only)
--json-schemaEnforce specific JSON schema on output
--max-turns NLimit agentic turns (print mode only)
--allowedToolsWhitelist tools (e.g., "Read,Grep,Glob")
--disallowedToolsBlacklist tools (e.g., "Edit,Write")

Official GitHub Action

- uses: anthropics/claude-code-action@v1

Handles GitHub context, comments, PRs automatically

Running Claude Code in CI without the -p flag will cause the process to hang waiting for interactive input. Always use -p for non-interactive pipelines.

CI/CD Best Practices

  • Session context isolation: The same Claude session that generated code is less effective at reviewing it — use a separate, independent review instance
  • Include prior review findings when re-running reviews after new commits, instructing Claude to report only new or still-unaddressed issues to avoid duplicate comments
  • Provide existing test files in context so test generation avoids suggesting duplicate scenarios already covered by the test suite
  • Document testing standards, valuable test criteria, and available fixtures in CLAUDE.md for CI-invoked Claude Code
The -p flag enables non-interactive mode for CI/CD. Use --allowedTools to restrict to read-only tools for safety. Combined with --output-format json and --json-schema, you can parse results programmatically.

4.1 — Explicit Criteria & Precision Prompting

Vague vs. Explicit Prompts

Vague: "Decide the moderation action: remove, review, or allow."
Explicit: 
Choose the action using these exact definitions:
- REMOVE: clear, unambiguous violation - doxxing,
  credible threat, clearly illegal content.
- REVIEW: may violate policy but needs a human -
  likely spam, borderline harassment.
- ALLOW: rude/blunt/off-topic but not a violation.

Tie-break: when unsure between REMOVE and REVIEW,
choose REVIEW.

Why This Matters

  • Vague "remove" leaves the label undefined — model over-fires, creating false positives
  • Explicit criteria + tie-break rule pull false positives back down on the same model
  • Three layers of precision:
    1. Criteria fix the decision (what each label means)
    2. Few-shot examples fix the format (exact output shape)
    3. Principles fix the intent (how to generalize)
Define each label with concrete, testable boundaries before applying it. Include a tie-break rule for ambiguous cases. This cuts false positives without fine-tuning.

4.2 — Few-Shot Prompting & Generalization

Few-Shot Examples

Supply a few labeled samples that fix the exact output format more reliably than instructions alone.

<examples>
<example>
Report: "User posted home address of ex-partner"
Output: REMOVE | Doxxing - exposure of private
  personal data with apparent intent to harm.
</example>
<example>
Report: "Threatening to crash the server"
Output: REVIEW | Ambiguous threat - likely
  refers to software, not physical harm.
</example>
<example>
Report: "This product is absolute garbage"
Output: ALLOW | Blunt criticism, not a
  policy violation.
</example>
</examples>

Generalization Principles

Add a short statement of intent so the model handles unseen, context-heavy edge cases.

PRINCIPLES:
- Protect people from real harm, not from
  uncomfortable opinions.
- Context matters: "I'll kill it" about code
  is not a threat.
- Public figures have higher threshold for
  criticism than private individuals.
- When in doubt, REVIEW - don't REMOVE.

Why All Three Together?

  • Criteria without format → right answers, parser can't read
  • Examples without intent → over-fit to shown cases
  • Together = accurate, machine-readable, robust to unseen
Few-shot examples (2–4 targeted cases) are more effective than detailed procedural instructions for fixing inconsistency. Don't add more instruction text when 2–3 concrete examples would resolve the issue.
Use 3-5 diverse examples wrapped in <example> tags. Show the exact output format. Add a principles block for generalization beyond the examples.

4.3 — Structured Output & Validation

}]

# Force this specific tool
tool_choice = {"type": "tool", "name": "classify_content"}

Validation & Retry Loop

MAX_RETRIES = 3
for attempt in range(MAX_RETRIES):
    response = client.messages.create(
        tools=tools,
        tool_choice={"type":"tool","name":"classify"},
        messages=messages
    )
    result = response.content[0].input

    # Validate
    if validate_schema(result):
        return result

    # Add error feedback and retry
    messages.append({"role":"user","content":
        f"Invalid output: {error}. Please retry."
    })

raise ValueError("Failed after retries")

Key Pattern

  • Use tool schema to define expected output
  • Force tool with tool_choice
  • Validate result against schema
  • Retry with error feedback if invalid

Schema Design: Nullable Fields & Limitations

Make Fields Nullable

When source documents may lack information, make fields nullable to prevent fabrication:

"birthdate": {
  "type": ["string", "null"],
  "description": "ISO date or null if not found"
}

Without null option, Claude may hallucinate a value rather than admit it's missing.

Enum "unclear" + "other" Patterns

  • Add "unclear" enum values for ambiguous cases — prevents forcing a wrong classification
  • Add "other" + detail string field for extensible categories the schema didn't anticipate
  • Include format normalization rules in prompts alongside strict schemas to handle inconsistent source formatting

JSON Schema Limitations

JSON schemas with tool_use eliminate syntax errors (malformed JSON, missing fields) but do NOT prevent semantic errors (wrong values, hallucinated data, incorrect classifications). You still need validation logic to check semantic correctness.

4.4 — Batch API & Multipass Processing

Message Batches API

  • 50% cost reduction on ALL token types (input, output, cache reads, cache writes, thinking)
  • Up to 100,000 requests or 256 MB per batch
  • SLA: 24 hours (practice: typically 5-30 min)
  • Each request processed independently
  • Failure of one request does NOT affect others
  • Order NOT guaranteed — use meaningful custom_id
  • Stacks with prompt caching: 50% batch + 90% cache = up to 95% savings

Limitations

  • No multi-turn tool calling within a single batch request (cannot execute tools mid-request and return results)
  • Use custom_id fields to correlate batch request/response pairs
  • Calculate submission frequency based on SLA: e.g., 4-hour windows to guarantee 30-hour total SLA with 24-hour processing

Use Cases

  • Large-scale evaluations, overnight reports, nightly test generation
  • Content moderation at scale, weekly audits
  • NOT for real-time interactions or blocking pre-merge checks

Multipass Pattern

Run Claude over the same input multiple times and compare/aggregate results:

# Pass 1: Initial classification
result1 = classify(content)

# Pass 2: Verification with different prompt
result2 = verify(content, result1)

# Pass 3: Confidence calibration
if result1 != result2:
    result3 = arbitrate(content, result1, result2)
    final = result3
else:
    final = result1  # High confidence

When to Use Multipass

  • High-stakes decisions (moderation, medical)
  • When single-pass accuracy isn't sufficient
  • Combine with batching for cost efficiency
Keep blocking pre-merge checks synchronous — do NOT route them through the Batch API. Batch API has a 24-hour SLA and is for latency-tolerant workflows only. A CI check that blocks a merge must return a result immediately.
Batch API gives 50% cost savings and stacks with caching for up to 95% savings. But never batch time-sensitive operations like pre-merge CI checks — those must be synchronous.

4.4b — Validation, Retry & Self-Correction Flows

Retry-with-Error-Feedback Pattern

When extraction fails validation, include the original document + failed extraction + specific errors in the retry prompt:

# Retry prompt structure:
"The previous extraction had errors:
- 'total_amount' was $1,234 but line items
  sum to $1,134 (difference: $100)
- 'date_signed' was null but appears on page 3

Original document: [full text]
Previous attempt: [failed JSON]

Please re-extract with corrections."

When Retries Are Ineffective

  • Information is absent from the source document — retrying won't create it
  • Format mismatches and structural errors — retries succeed with error feedback

Self-Correction Validation Flows

Extract both calculated and stated values to detect discrepancies:

{
  "stated_total": 1234.00,
  "calculated_total": 1134.00,
  "conflict_detected": true,
  "line_items": [...]
}

detected_pattern Field

  • Track which code constructs trigger findings in a detected_pattern field
  • Enables systematic analysis of false positive patterns when developers dismiss findings
  • Feedback loop: analyze dismissals → improve prompts for those patterns

Prompt Refinement on Samples

  • Refine prompts on a sample set before batch-processing large volumes
  • Maximize first-pass success to reduce iterative resubmission costs
Don't retry when the info isn't in the source document. DO retry when the model made a format/structural error — include the original document, failed extraction, and specific validation errors in the retry prompt.

4.5 — Temperature & Sampling Parameters

Temperature

  • Range: 0.0 – 1.0 for Claude (OpenAI uses 0–2.0)
  • Default: 1.0 (maximum randomness by default)
  • Controls randomness via softmax scaling of token logits
  • Low (0.0–0.3): Classification, data extraction, code generation, math
  • High (0.7–1.0): Creative writing, brainstorming, diverse outputs
  • → temperature: 0 does NOT guarantee deterministic output (floating-point math, MoE architecture)

top_p & top_k

  • top_p (nucleus sampling): considers tokens whose cumulative probability ≤ p
  • top_k: NOT available in native Claude API (only via Vertex AI / Bedrock)
  • → Alter temperature OR top_p, NOT both simultaneously

Deprecation (Opus 4.7+)

  • Temperature is deprecated on Claude Opus 4.7+
  • Replaced by effort parameter: low | medium | high
# Low temperature — precise, factual tasks
response = client.messages.create(
    model="claude-sonnet-4-6",
    temperature=0.0,
    messages=[{"role": "user", "content": "Extract the date: 'Meeting on Jan 15'"}]
)

# High temperature — creative, diverse outputs
response = client.messages.create(
    model="claude-sonnet-4-6",
    temperature=0.9,
    messages=[{"role": "user", "content": "Write a tagline for a coffee brand"}]
)

5.1 — Context Preservation & Optimization

The Problem

Long conversations lose details (numbers, dates, IDs). After auto-compact, nuance disappears.

Progressive summarization silently corrupts transactional data — amounts, dates, order numbers become vague paraphrases. Never use progressive summarization on conversations with transactional data. Instead, extract specifics into a persistent case facts block.

Case Facts Block

A persistent structured block that keeps critical details alive across turns:

# CASE FACTS (do not remove)
- Customer: Jane Doe (ID: CUST-4421)
- Order: NP-100190
- Issue: Return request for boots
- Account Tier: Enterprise
- SLA: 4-hour response
  • Place at start or end of context (primacy/recency effect)
  • Write to file to survive /compact
  • Keep it small and high-signal
  • Include case facts verbatim in every prompt — never summarize them

Trimming Tool Outputs

  • Summarize a 500-row query into the 5 relevant fields
  • Return only fields Claude needs for next step
  • Use semantic identifiers (slugs, UUIDs) not opaque refs
  • MCP output limit: 25,000 tokens (warning at 10,000)

Context Placement

PositionEffect
Start of contextPrimacy effect — high recall
End of contextRecency effect — high recall
Middle of context"Lost in the middle" — lower recall
Place key summaries/findings at the beginning of long inputs to combat the "lost in the middle" effect.
Keep critical info at the start or end of context (primacy/recency). Write case facts to a file so they survive /compact. Never summarize transactional data — include verbatim.

5.2 — Escalation & Ambiguity Resolution

Three Valid Escalation Triggers

#TriggerExample
1Explicit human requestCustomer says "Let me talk to a manager"
2Policy gapNo clear rule applies to this situation
3Inability to make progressStuck, can't proceed with available tools/info

Golden Rule

Request clarification instead of guessing.

Invalid Escalation Triggers (Anti-Patterns)

  • Customer frustration / sentiment — frustrated customers don't always need escalation
  • Model's self-reported confidence score — LLM confidence is poorly calibrated, unreliable trigger
  • Case complexity — escalate on policy gaps, not just because a case is hard

Structured Escalation Handoff

{
  "customer_id": "CUST-4421",
  "issue_summary": "Billing dispute on order NP-100190",
  "root_cause": "Double charge during system outage",
  "attempted_resolution": "Verified charge, found duplicate",
  "recommended_actions": [
    "Issue refund for duplicate charge",
    "Apply 10% courtesy credit"
  ],
  "confidence": 45,
  "escalation_reason": "Policy unclear on auto-refund threshold"
}

Include: customer ID, issue summary, root cause, attempted resolution, recommended actions, and why escalated.

A structured escalation with defined fields (ID, summary, root cause, recommended actions) is ALWAYS better than passing just the customer ID or an unstructured text summary. Escalate on policy gaps, not complexity or sentiment.

5.3 — Error Propagation in Multi-Agent Systems

Structured Error Types

# Propagate structured errors with:
# - error type (what went wrong)
# - partial results (what succeeded)
# - alternatives (what to try next)

{
  "isError": True,
  "errorType": "timeout",
  "partialResults": {"classified": True, "enriched": False},
  "alternatives": ["retry_with_cache", "skip_enrichment"],
  "isRetryable": True
}

Retry-Local Pattern

  • Subagents retry locally (handle transient errors internally)
  • Only send unresolved errors up to coordinator
  • Coordinator decides: retry subagent, try alternative, or fail gracefully

Critical Distinction

ScenarioIs Error?Action
Timeout (503)Yes, retryableRetry with backoff
Not Found (404)Yes, NOT retryableStop, report
Empty resultsNOValid response, proceed
A timeout is an infrastructure error (retry). "No data found" is a valid result (don't retry). Subagents should silently retry transient errors; only propagate unresolved failures. Never terminate the entire pipeline on a single tool failure — degrade gracefully and annotate gaps.

5.5 — Human Review & Confidence Calibration

Confidence-Based Routing

def route_decision(result, threshold=70):
    if result["confidence"] >= threshold:
        return auto_approve(result)
    else:
        return request_human_review(result)

# Per-field confidence
{
  "name":     {"value": "John Doe", "confidence": 95},
  "birthdate":{"value": "1985-03-15","confidence": 60},
  "address":  {"value": "123 Main St","confidence": 40}
}
# Only review low-confidence fields

Stratified Sampling

Don't rely on aggregate accuracy. Evaluate per field and per document type.

  • Sample from each confidence stratum (high/medium/low)
  • Detect if "high confidence" is actually accurate
  • Find edge cases in all ranges
  • Validate calibration (is 90% confidence really 90% accurate?)

Evaluation Tiers

90-100Auto-approve, spot-check 5%
70-89Light review, sample 20%
50-69Full human review
<50Always escalate to human

Independent Review > Self-Review

A separate Claude instance with fresh context catches errors that self-review misses. The same instance reviewing its own output tends to rationalize its original errors rather than finding them. Always use an independent reviewer for high-stakes outputs.
  • Self-review: Same context, same biases — rationalized errors persist
  • Independent review: Fresh context, no prior commitment — catches actual mistakes
  • Implement as: spawn a new API call with only the output to review (no conversation history)

Multi-Pass Review Architecture

  • Per-file local passes: Analyze each file individually for local issues (bugs, style, security)
  • Cross-file integration pass: Separate pass examining data flow and dependencies across files
  • Verification pass: Model self-reports confidence alongside each finding for calibrated routing
  • Validate accuracy per document type and per field before automating high-confidence extractions

5.6 — Information Provenance & Uncertainty Handling

Claim-Source Mapping

Map every claim to its source (URL, doc name, evidence excerpt).

{
  "claim": "30-day return window applies",
  "sources": [
    {
      "document": "returns-policy.md",
      "excerpt": "Items may be returned within 30 days",
      "publication_date": "2024-01-15"
    }
  ],
  "confidence": 95,
  "status": "confirmed"
}

Citation Types

  • document_citation — From uploaded documents
  • web_search_result_location_citation — From web search
  • Always include quoted_text for verification

Handling Conflicting Sources

  • Keep conflicting info from multiple sources — don't pick one
  • Always include publication dates for temporal context
  • Flag where sources disagree for reviewer attention

Confirmed vs. Contested Report

## Confirmed Findings
- 30-day return window [Source A, Source B]
- Free shipping over $50 [Source A]

## Contested Findings
- Refund processing time:
  - Source A (2024-06): "3-5 business days"
  - Source B (2023-11): "7-10 business days"
  - Note: Source A is more recent

## Unverified (Single Source)
- Holiday return extension [Source C only]

Temporal Data & Coverage Annotations

  • Require publication/collection dates in structured outputs to prevent temporal differences from being misinterpreted as contradictions
  • Render different content types appropriately: financial data as tables, news as prose, technical findings as structured lists
  • Structure synthesis output with coverage annotations indicating which findings are well-supported vs. which have gaps due to unavailable sources
  • Require subagents to include metadata (dates, source locations, methodological context) in structured outputs for accurate downstream synthesis
Never silently pick one conflicting source. Present both with publication dates and let the reviewer decide. Distinguish confirmed, contested, and single-source claims. Always require temporal context in structured outputs.
